# Airloom

M5Stack NanoC6をZigbeeコーディネーターとして使い、温湿度センサーの値をWi-Fi経由でローカルのHTTP受信先に送る試作です。

## 環境

- [M5Stack NanoC6](https://docs.m5stack.com/en/core/NanoC6): ESP32-C6FH4、フラッシュ4 MB。
- ESP-IDF v5.5.4、ESP Zigbee SDK v2.0.4。[SDKのリリースノート](https://github.com/espressif/esp-zigbee-sdk/blob/main/RELEASE_NOTES.md)記載の組み合わせです。
- [ESP32-C6の無線共存](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-guides/coexist.html)を使用します。Wi-FiとZigbeeは無線を共有するため、実際の受信欠落は実機で評価する必要があります。
- Wi-Fi対応版はESP-IDF標準の拡大版単一アプリ領域を使用します。NVSとPHY領域の位置・サイズは標準版と同じです。

## ビルドと書き込み

ESP-IDFの環境を有効化したターミナルで実行します。ポートは実機に合わせてください。

```powershell
cd zigbee
idf.py build
python configure_local.py
idf.py build
idf.py -p COM6 flash monitor
```

設定スクリプトで2.4 GHz Wi-FiのSSID、パスワード、HTTP受信先URL、送信間隔を入力します。パスワードは画面に表示しません。設定はGit管理外の `zigbee/sdkconfig` に保存され、ファームウェアにも含まれます。これらを公開しないでください。テスト時は30秒、運用時は86400秒などに設定できます。鮮度の閾値は `idf.py menuconfig` の「Airloom HTTP upload」で変更できます。

Wi-Fiは常時接続し、Zigbee初期化後に共存を有効化してから初回接続を試みます。初回接続を最大20秒待ち、失敗してもZigbeeの起動は続けます。Wi-Fi切断時は送信間隔に関係なく再接続を試し、失敗が続く場合は30秒間隔で再試行します。HTTP送信に失敗した場合は10秒後に再試行し、成功後は設定した送信間隔で送ります。常時接続による消費電力は未測定です。

ペアリング情報はNVSに保存します。既存のペアリングを保持する更新ではNVSを消去せず、`erase-flash` は実行しないでください。今回の実機では、診断用ファームウェアとの切り替えをアプリ領域だけに書き込み、通常版へ戻した後も再ペアリングなしで受信できることを確認しました。

受信器はPython標準ライブラリだけで動作します。NanoC6とは別のWindows PCで以下を実行し、ゲートウェイのURLにはそのPCのLANアドレスを指定します。

```powershell
python receiver/server.py --host 0.0.0.0 --port 8080 --file measurements.jsonl
```

ブラウザーで `http://<PCのLANアドレス>:8080/` を開くと最新の受信値と鮮度を確認できます。受信器は認証や暗号化を備えないため、信頼できるローカルネットワークで使用してください。詳細は [receiver/README.md](receiver/README.md) を参照してください。

受信を続ける間はサーバーのプロセスを起動しておく必要があります。PC起動時の自動起動は実装していません。PCのネットワーク接続が一時的に切れても、サーバーが動作し続け、同じLANアドレスで復旧すればNanoC6のHTTP再試行で受信を再開します。

## センサーの登録と値

NanoC6のボタンを押すと180秒間だけ新規参加を受け付けます。その間にセンサーを製品の手順に従ってペアリング状態にします。今回のセンサーではRESET操作で参加しましたが、操作の詳細は製品の説明書を確認してください。

実機の識別情報はメーカー `Zbeacon`、モデル `TH01`、エンドポイント1でした。標準温度クラスター `0x0402` と湿度クラスター `0x0405` の報告を受信しました。温度・湿度はそれぞれ100分の1 °C、100分の1 %RHとして変換します。電池残量と電圧も取得可能でした。クラスター `0xef00` も検出していますが、その形式は未解析です。

温湿度と電池値はRAMに保持し、各値のゲートウェイ受信からの経過時間を送ります。測定時刻ではありません。再起動すると保持値は消え、新たな報告を待ちます。未取得の温湿度とその経過時間は0にせずnullとし、未取得の電池項目は送信しません。受信器は受信後の経過時間も加えて温湿度の鮮度を判定します。現在の保持対象は1台分で、別センサーの報告を受けると保持対象を置き換えます。

## 実機確認と未確認事項

2026年10月27日時点で、本体コードへの常時接続方式の反映、ペアリングを保持した1時間の連続動作、NanoC6側のWi-Fi切断からの復旧、Windows側の通信断からのHTTP受信再開を確認しました。以下の診断記録には対策前の失敗も含みます。

- COM6のESP32-C6FH4 revision v0.2に書き込み、ハッシュ照合を確認。
- 温度28.98 °C、湿度55.01 %RH、電池100%、3.0 Vを受信。再起動後、再ペアリングなしで温度28.88 °C、湿度54.70 %RHを再受信。
- Wi-Fi対応版への書き込み後も再ペアリングなしで湿度54.99 %RHを受信。
- 旧版では切断理由201（アクセスポイント未検出）が繰り返され、Wi-Fiのみの一時的なファームウェアによるスキャンでも0件でした。NanoC6の近くに2.4 GHzテザリングを置いても0件でした。ESP-IDF v5.5.4の公式スキャン例を独立設定でビルドした場合も0件でした。同じ場所のPCでは設定したSSIDの2.4 GHz電波を検出しています。原因は未確定です。接続失敗後にもZigbeeの湿度報告を受信しました。
- 旧版ではHTTP送信、送信中のZigbee受信、Wi-Fi切断後の接続回復、長時間安定性を確認できませんでした。後続の共存試験は以下に記録しています。

### Wi-Fi未検出の切り分け

2026年10月27日に、ESP-IDF v5.5.4の公式スキャン例を独立設定で実行しました。既定の全チャンネル・アクティブスキャンは0件でした。同じ環境でPCが検出したチャンネル2について、隠しSSIDを含む1秒間のパッシブスキャンも0件でした。アクティブスキャンとパッシブスキャンの動作は[公式Wi-Fi資料](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-guides/wifi.html)を参照してください。

両ファームウェアは同じNVS内のRF校正データを使うため、診断例のみ校正データの保存・読み込みを無効にして、消去せずにフル校正を実行しました。どちらのスキャンも0件でした。この設定は[公式RF校正資料](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-guides/RF_calibration.html)に説明されています。

さらに診断例でチャンネル2の一時アクセスポイントを起動しました。NanoC6は起動をログに出しましたが、PC側でスキャンを開始しても周囲の15件は検出され、診断用アクセスポイントは検出されませんでした。USBを接続し直した後も、アクティブ・パッシブスキャンは0件で、PCは診断用アクセスポイントを検出しませんでした。診断はNVSを全消去せずに実施し、終了後は通常のファームウェアを書き戻しました。

ESP32-C6のWi-Fiに関する公開不具合報告はありますが、今回と同じ構成・原因の確定した事例は確認できていません。PC側ではスキャン完了通知を確認していなかったため、アクセスポイントが表示されなかった結果だけではNanoC6の送信不能とは判断できません。[NanoC6公式仕様](https://docs.m5stack.com/en/core/NanoC6)では内蔵セラミックアンテナを使用しています。

### 診断条件を揃えた再検証

- A-to-CからC-to-CへUSBケーブルを交換後、実機と同じ4 MB・パーティション構成の単独Wi-Fi診断を使用しました。Wi-Fi設定のNVS保存と保存済みRF校正値の使用は診断側で無効にしました。診断時の書き込みはアプリ領域に限り、NVSは消去していません。
- ESP-IDF 5.5.4と5.4.4で同じ診断コードを実行し、USBリセット後のアクティブ・パッシブスキャンはいずれもAPIの成功を確認したうえで、各3回とも0件でした。同じ時間帯にPCはスキャン完了を確認し、2.4 GHzの複数のアクセスポイントを検出しました。Wi-Fiファームウェアの版は異なりますが、両SDKに含まれるESP32-C6用PHYライブラリは同一です。
- 5.5.4でソフトウェア再起動を挟むと、3回のスキャンで15〜18件を検出しました。その後はUSBリセット後の11秒待機、さらに5秒待機でもアクセスポイントを検出し、設定済みSSIDを見つけてWi-Fi接続とIPアドレスの取得に成功しました。再起動の種類や待ち時間だけが原因とは特定できていません。
- 元のゲートウェイに戻すと、再ペアリングなしで温湿度を受信しましたが、Wi-Fi接続は理由201（アクセスポイント未検出）で繰り返し失敗しました。同じゲートウェイの保存済みRF校正だけを無効にした一時ビルドでも、センサーを受信した後の接続は理由201で失敗しました。
- [EspressifのZigbeeとWi-Fiの共存に関する報告](https://github.com/espressif/esp-zigbee-sdk/issues/415)と公式ゲートウェイ例に基づき、一時ビルドで `esp_coex_wifi_i154_enable()` を試しました。Zigbee初期化後の呼び出しではセンサーを受信しましたがWi-Fiは理由204（ハンドシェイクのタイムアウト）で失敗しました。初期化前に呼び出し、センサー値がない間も接続を試す診断ではIP取得に成功した試行と理由204で失敗した試行の両方があり、安定した対策とは確認できませんでした。空の診断ではHTTP送信していません。
- [ESP-IDFの共存仕様](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-guides/coexist.html)は、Wi-FiとZigbeeが無線回路を共有するため、一部の同時動作は性能が不安定になり得ると説明しています。この再検証時点では失敗の直接原因や長時間安定性は未確定で、ゲートウェイからのHTTP送信も未確認でした。後続の共存試験でHTTP送信を確認しました。
- 診断後のNVS領域は診断中の先行する読み出しと一致しました。初回フラッシュ退避から最初の診断後読み出しまでに差分があり、その間には通常ファームウェアの起動も含まれるため、差分の発生時点は未特定です。
- 検証後は元のゲートウェイをアプリ領域へ書き戻し、書き込みデータのハッシュを検証しました。最終起動時に `factory_new=0` を確認しています。

### Wi-FiとZigbeeの共存試験

- 既存のペアリングを保持し、保存領域の退避後、一時ビルドでESP Zigbee SDK 2系のゲートウェイ例に近い起動順を試しました。Zigbee初期化後に共存APIを有効化し、Wi-Fiの初回接続を試してからZigbeeネットワークを開始します。イベントループのスタックは4096バイトにし、Wi-Fiを停止せず維持しました。
- 初回のWi-Fi接続は理由204で失敗しましたが、Zigbee開始後の再接続でIPアドレスを取得しました。5分間の観測で、その後のWi-Fi切断はなく、センサー報告26回とHTTP 200の送信18回を確認しました。送信間隔は試験用の15秒で、実際のセンサー値のみを送信しました。
- 同じSSIDにある2つの2.4 GHzアクセスポイントをそれぞれ固定し、共存APIを使いつつ、Wi-Fiを開始・停止する方式も各150秒試しました。試験用の待機間隔は10秒です。接続先AではIP取得6回・HTTP 200が5回、理由204が3回・理由4が2回記録されました。接続先BではIP取得4回・HTTP 200が4回、理由204が5回記録されました。理由8は明示的なWi-Fi停止に伴う通知です。
- 起動順、共存API、イベントループのスタック、接続維持をまとめて変更したため、成功の寄与を個別には特定できていません。センサー報告の取りこぼしと消費電力は未測定です。この試験の後はいったん通常版を戻し、`factory_new=0` とセンサーからの湿度報告を再確認しました。

### 常時接続版の切断復旧試験

本体と同じコードに一度だけ切断を発生させる試験用処理を加え、実際のセンサー値のHTTP送信成功後に `esp_wifi_disconnect()` を実行しました。切断後の最初の接続は理由204で失敗しましたが、約31秒後にIPアドレスを再取得し、その後のHTTP送信2回とセンサー報告を確認しました。ペアリングは維持されました。

送信間隔を86400秒にした一時ビルドでも、同様の切断から約31秒後にIPアドレスを再取得し、その後のセンサー報告を受信しました。これは再接続が送信間隔と独立していることを示す試験であり、24時間間隔の送信自体は確認していません。これらはNanoC6側で発生させた切断で、アクセスポイントの電源断や電波断の試験ではありません。

### 常時接続版の1時間試験

切断を発生させる試験処理を含まない本体ファームウェアを、ペアリング用NVSを消去せずに書き込みました。送信間隔30秒で1時間監視し、初回接続の理由204による失敗と再接続の後は、Wi-Fi切断や再起動を記録せず、センサー報告79件とHTTP 200による送信117回を確認しました。受信側にも同じセンサーIDのデータが1時間内に117件保存されました。最後のセンサー報告は起動後約58分53秒でした。

この1時間は実機で確認した範囲であり、それより長い連続動作、消費電力、アクセスポイントの電源断、センサー報告の取りこぼしは未検証です。

### 受信サーバーの継続受信とWindows側の通信断からの復旧

Windows PCで受信サーバーを起動し、NanoC6から約30秒間隔で温湿度データを継続受信しました。各HTTP送信は保持中の最新値を送るため、毎回センサーの新しい報告があることを意味しません。値ごとの経過時間で更新の有無を確認します。

2026年10月27日13:40〜13:43（日本時間）に、受信先の有線アダプターを45秒間無効化してから再有効化しました。対象アダプターを識別子で限定し、切断中もPC上で動く復旧処理を用意して実施しました。

- 切断中、NanoC6は `ESP_ERR_HTTP_CONNECT` を記録しました。
- アダプターは同じLANアドレスで復旧し、復旧確認の約0.65秒後にHTTP 200で受信が再開しました。これは今回の観測値であり、復旧時間の保証ではありません。
- 切断前の最終受信から再開までの間隔は約51.6秒で、再開後は約30.1秒間隔で4回連続受信しました。
- 受信サーバーは同じプロセスで待ち受けを継続し、PC・NanoC6・受信サーバーの再起動は不要でした。ペアリングも保持し、新しいZigbeeの湿度報告を受信しました。温度は保持値が送られており、この短時間の試験中に新しい温度報告は確認していません。

この試験はWindows側の受信経路の切断を検証したものです。NanoC6側のWi-Fi切断復旧試験とは別であり、アクセスポイントの電源断試験ではありません。
